# План анімацій LaresCare

Статус: пропозиція до реалізації, 2026-09-24. Анімації за цим планом ще не реалізовано.

## Напрям

Спокійний, уважний рух для старших людей і їхніх родин. Один характерний жест Лара, короткі пояснювальні акценти та чіткий відгук елементів керування. Читання, навігація й заявка доступні одразу; рух не змінює погоджену композицію, текст чи геометрію персонажа.

## Поточна реалізація

- Кнопки мають CSS transitions; внутрішні стрілки рухаються вправо, зовнішні — вгору вправо. Shared CSS вже враховує reduced motion.
- Нові сторінки використовують `src/components/landing/LandingHeader.tsx`; legacy `src/components/MobileNav.tsx` не є ціллю цього плану.
- Форма має native radio, приховане optional note, стани submitting/success/error й live announcements.
- FAQ — native `<details open>`; поточний початковий відкритий стан зберігаємо.
- У `public` не знайдено готових GIF/WebM/MP4/Rive/Lottie для Лара. Використовуємо наявну графіку; морфінг обличчя не плануємо.
- Home вже має responsive scale на телефоні/heroArt та translateX на Ларі. Нові keyframes не можуть перезаписувати ці transform.

## Що зберігаємо статичним

Основний текст, фото, заголовки, загальні секції та картки переваг. Для неінтерактивних карток не додавати hover lift, що створює хибне враження клікабельності. Не потрібні паралакс, scroll hijacking, нескінченне плавання Лара, пульсація CTA, autoplay аудіо, друк тексту по літерах, анімація кожної секції або переходи між сторінками. Speak / Type у персиковому блоці — пояснювальні підписи, а не робочі кнопки чату.

FAQ у першому проході залишається native без анімації висоти. Якщо пізніше потрібне плавне розкриття, спочатку окремо перевірити progressive enhancement і поведінку клавіатури у цільових браузерах.

## Технічні межі

- Почати з CSS transitions/keyframes та невеликого `IntersectionObserver` client-компонента для запуску один раз. Усі сторінки не переводити в client components. Нових motion dependencies у P1/P2 не додавати.
- Motion tokens: fast 120ms, feedback 180–220ms, scene 420ms; ease-out `cubic-bezier(.22,1,.36,1)`. Особливий жест Лара — 600ms. Не використовувати bounce/elastic.
- Обгортка руху має бути окремою від шару, що керує responsive scale/translate. Масштаб телефону, позиція Лара −16px і caption −36px мають залишитися точними.
- Базовий CSS показує повний фінальний контент. Відсутність JS, IntersectionObserver або запуску анімації не повинна приховувати текст/зображення. Це не обіцянка додати no-JS submit або menu до нинішніх React-компонентів.
- Observer від’єднується після першого запуску; якщо елемент вийшов з viewport або вкладка стала прихованою — завершити декоративний рух у фінальній позиції. Не підтримувати постійні rAF/interval/scroll loops.
- `prefers-reduced-motion` враховувати і в CSS, і при запуску JS; зміна системної настройки під час перегляду завершує рух. Жодних миготінь чи декоративних циклів довших за 5 секунд.
- Меню: зберегти Escape, повернення фокусу, aria-expanded і закриття після переходу. Не затримувати навігацію заради exit-animation.
- Форма: повідомлення `role=status`/`role=alert` не чекатимуть анімації. Нативні radio, disabled під час запиту, збереження введеного note і чинний payload лишаються без змін. Помилки не трясти.

## Критерії приймання

- 360/390/768/1024/1440px: немає нового переповнення, перекриття тексту, стрибків фото чи зміни цільових областей кліку.
- Нічого не треба чекати для читання, переходу або взаємодії з формою. З reduced motion всі декоративні сцени статичні.
- Немає анімаційного layout shift; зображення й текст не приховані до scroll event. Відключений observer залишає цілісну сторінку.
- CSS/JS бюджет і Performance trace порівняти з базою за однакових умов; немає нового постійного CPU-навантаження чи помітного ривка при прокручуванні. Smoothness на desktop не називати доказом FPS на реальному старому телефоні.
- Після останнього коду: lint, typecheck; для змін форми — наявні `test:contact`. Production build у відокремленому середовищі/після погодженого завершення preview, щоб не перезаписати активний `.next`.
- Оцінка Impeccable audit — лише після реалізації та перевірки, не з самого плану.
